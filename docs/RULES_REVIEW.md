# Система строительных проверок Build Sense и FreeCAD SnipChecker: анализ и проект улучшения

Дата: 27.10.2026. Исследуемая версия: ветка `konkurs-sistema` репозитория `sneyri/freecad-snip-checker` (коммит `662ce52`).
Статус документа: **исследование и проект**. Внедрены только исправления приоритета P0 (раздел 7): п. 6.2 по каждому этажу с «требуется проверка» для наклонных потолков, область применения СП 55, «не применялось» вместо пустого PASS — тесты `tests/p0.test.js`. Остальные предложения не внедрены.

## 1. Анализ существующей системы проверок

### 1.1. Где хранятся и выполняются проверки

| Место | Что делает |
|---|---|
| `js/validation/validationEngine.js` | 19 встроенных проверок (`CHECKS`): 8 геометрических `GEO-*`, 11 конструктивных `STR-*`; запуск всех проверок (`validate`), итог, подсветка, исправления (`applyFix`) |
| `js/objects/support.js` | опирание элемента: доля опирания, зазор до опоры, допуск отметок `LEVEL_TOL = 0,02 м` |
| `js/validation/metrics.js` | вычисляет параметры модели для правил норм (`building.*`, `room.*`, `wall.*` и др.) |
| `js/rules/checker.js` | сравнивает параметры с правилами: операторы, единицы, условия применимости, статусы PASS / FAIL / NOT VERIFIED |
| `js/rules/ruleRegistry.js`, `data/rules/*.json`, `js/rules/builtinRules.js` | реестр правил: СП 55.13330.2016 (8 правил), демонстрационные (4), пользовательские |
| `js/ui/problems.js`, `js/ui/rulesPanel.js` | показ результатов, фильтры, переход к элементу |
| `js/io/freecadExport.js` | в экспорт для FreeCAD попадает только сводка (`validationSummary`: число ошибок и предупреждений), без результатов по элементам |
| `freecad/import_house.FCMacro`, `tests/freecad_real_test.py` | макрос строит модель, но **проверок во FreeCAD не выполняет**. Тест проверяет только корректность импорта: габариты, вырезы, BIM-коды, IFC |

Вывод: «FreeCAD SnipChecker» сейчас — это реестр правил и проверка норм внутри Build Sense плюс передача модели во FreeCAD. Сам FreeCAD нормы не проверяет и результатов проверки не получает.

### 1.3. Что уже сделано хорошо

- Правила норм вынесены в JSON с документом, пунктом, источником, статусом сверки и условиями применимости.
- PASS/FAIL выдаётся только для сверенных и пользовательских правил. Несверенные и демонстрационные дают NOT VERIFIED.
- Если данных не хватает (нет параметра или не определена применимость), результат — NOT VERIFIED, а не PASS.
- Есть перевод единиц, валидация формата правил и пользовательские правила с пометкой «учебное ограничение».
- Конструктивные проверки сформулированы как «потенциальная проблема, требуется инженерная проверка».
- Пороги эвристик в основном вынесены в «учебный профиль» и не выдаются за нормы.

## 4. Предлагаемая архитектура правил

### 4.1. Главный принцип: разделить три оси

Сейчас уровень «ошибка / предупреждение» одновременно означает и важность, и достоверность. Предлагается хранить их отдельно.

1. **Вид правила `kind`** — откуда берётся вывод:
   - `geometry` — дефект модели, доказывается геометрией;
   - `norm` — пункт нормативного документа (только со статусом сверки);
   - `constraint` — проектное ограничение пользователя (учебный профиль, задание на проектирование);
   - `heuristic` — признак возможной ошибки модели;
   - `risk` — потенциальный конструктивный риск, нужна оценка специалиста.
2. **Важность `severity`**: `critical` (модель нельзя использовать дальше), `major`, `minor`, `info`.
3. **Результат `status`**:

| Статус | Когда | Пример |
|---|---|---|
| `PASS` | правило применимо, данных достаточно, требование выполнено | высота всех помещений ≥ 2,5 м |
| `FAIL` | правило применимо, данных достаточно, требование нарушено | помещение 2,4 м при 2,5 м |
| `NOT_APPLICABLE` | правило не относится к объекту | СП 55 для 5-этажной секции; балок нет |
| `INSUFFICIENT_DATA` | правило применимо, но в модели нет нужных данных | не задан тип помещения; нет пола |
| `RULE_NOT_VERIFIED` | значение правила не сверено с действующей редакцией | п. 9.18; кандидаты СП 54 |
| `NEEDS_REVIEW` | данных хватает, но вывод зависит от неформализуемых условий | мансардное помещение, наклонный потолок |
| `CHECK_ERROR` | сбой самой проверки | исключение в коде |

Правило отображения: зелёный — только `PASS`; красная «ошибка» — только `FAIL` у `geometry` и у сверенной `norm`; у `heuristic` и `risk` — «предупреждение / требуется проверка»; все остальные статусы — нейтральные, каждый со своей причиной. Счётчик «пройдено» не включает `NOT_APPLICABLE`.

**Какие проблемы это решает:** 2.3, 2.4, 2.5, 2.10. Теперь по итогу видно, что модель «доказанно неверна», а что «вероятно стоит проверить».

### 4.2. Формат правила

```json
  "limitations": ["Отделка пола и потолка в модели не задаётся", "Помещения — условные зоны"],
  "source": {
    "document": "СП 55.13330.2016", "clause": "6.2", "edition": "Изменение № 2, приказ Минстроя России от 17.05.2023 № 350/пр",
    "effectiveFrom": "2023-06-18", "url": "…"
  },
  "verification": { "status": "verified", "checkedOn": "2026-10-26", "checkedBy": "автор", "recheckAfter": "2027-10-26" },
  "fix": "Увеличьте высоту этажа или уменьшите толщину перекрытия; проверьте отделку"
}
```

Новое по сравнению с текущим форматом:
- `kind` и `severity` — разделение видов и важности (см. 4.1);
- `target` — правило для каждого помещения или элемента, а не для «здания в целом» (решает 2.1);
- `scope.requires` — зависимость от правила области применения документа (решает 2.2);
- `undecidable` — явные случаи, когда вывод сделать нельзя (решает 2.7);
- `method` и `limitations` — как считается параметр и чего модель не знает (решает 2.6);
- отдельные `edition`, `effectiveFrom`, `recheckAfter` (решает 2.13);
- `tolerance` — допуск сравнения в единицах правила, а не скрытый `EPS`.

### 4.3. Область применения документа

Правило п. 1.1 СП 55 переводится в правило вида `scope`: `DOC-SCOPE-SP55` («свод правил применим, если ≤ 3 надземных этажей и высота ≤ 20 м»). Его результат — «документ применим / не применим», а не PASS/FAIL. Если документ не применим, все правила с `scope.document = "СП 55.13330.2016"` получают `NOT_APPLICABLE` с причиной «вне области применения СП 55, п. 1.1», а пользователь — подсказку: «для многоквартирных домов проверяйте по СП 54.13330.2022 (правила пока не сверены)».

### 4.4. Параметры модели с методикой

Каждый параметр в `metrics.js` получает описание методики и уровень точности: `exact` (по геометрии), `estimate` (оценка по модели), `declared` (введено пользователем). Например:
- `room.clearHeight` — `estimate`: по каждому помещению, без отделки;
- `room.area` — `declared` для зон, `estimate`, если помещение построено по контуру стен (после внедрения пункта 3 плана развития);
- `building.glazingRatio` — только справочно; для п. 9.18 нужен параметр по помещению `room.glazingRatio`.

Правило с `kind: "norm"` может выдать `FAIL` по параметру `estimate`, но в сообщении указывается методика. С параметром `declared` правило выдаёт результат с пометкой «по данным пользователя».

### 4.5. Объяснимые и сгруппированные результаты

Единый формат результата для Build Sense, экспорта и FreeCAD:

```json
{
  "ruleId": "STR-SLABS-SPAN", "ruleVersion": 1, "kind": "heuristic", "severity": "minor", "status": "FAIL",
  "elements": ["slab-2", "slab-3", "slab-4", "slab-5"],
  "message": "Пролёт перекрытия 8 м больше ориентира профиля 7 м",
  "cause": { "parameter": "slab.span", "actual": 8, "expected": "<= 7", "unit": "m", "method": "меньший размер плиты" },
  "source": { "type": "profile", "field": "maxSlabSpan" },
  "fix": "Добавьте промежуточную опору или проверьте расчётом",
  "groupKey": "STR-SLABS-SPAN|8|7"
}
```

- **Группировка** по `groupKey` (правило + причина + значения): 4 одинаковые плиты — одно сообщение со списком элементов (решает 2.9).
- **Демонстрационные правила** по умолчанию свёрнуты в одну строку «демо-правила: N сравнений, не нормы».
- **Пороги эвристик** из кода переносятся в профиль с полем `origin: "heuristic"` и подписью «ориентир, источник не нормативный» (решает 2.8).

### 4.6. Передача результатов во FreeCAD

Экспорт получает блок `checks: [...]` в формате 4.5. Макрос записывает объекту свойства `BuildSenseIssues` (список `ruleId: status`) и `BuildSenseWorstStatus`, а в отчёт импорта — сводку по видам правил (решает 2.12). Это не проверка во FreeCAD, а перенос результатов. Повторную проверку уже во FreeCAD или по IFC см. в 4.7.

### 4.7. Что можно взять из IDS (buildingSMART)

IDS описывает требования к информации в модели IFC: **applicability** (к каким объектам относится требование) и **requirements** (что у них должно быть). Требования строятся из фасетов Entity, Attribute, Classification, Property, Material, PartOf.

Что применимо в проекте:
- **разделение «к чему применяется» и «что требуется»** — это поля `target` + `applicability` и `check` в формате 4.2;
- **проверки полноты данных**, а не только чисел: «у каждой несущей стены задан материал», «у каждого помещения задано назначение», «у каждого элемента есть BIM-код», «каждый элемент относится к этажу» (аналог PartOf). Такие проверки устраняют причину `INSUFFICIENT_DATA` до проверки норм;
- **фасеты как словарь**: Entity → тип элемента, Attribute → размеры и имя, Classification → категория и BIM-код, Property → параметры, Material → материал, PartOf → этаж или стена-основа.

Что не заявляется: совместимость с IDS не реализована и не проверена; файлов `.ids` проект не создаёт и не читает. Возможный следующий шаг — выгружать требования полноты данных в `.ids` и проверять IFC, который сохраняет макрос. Подходящий инструмент для такой проверки (например, из экосистемы IfcOpenShell) нужно подобрать и испытать отдельно.

## 8. Ограничения и необходимые экспертные проверки

- **Тексты норм.** Пп. 5.11 и 5.12 СП 54, исключение для мансард в п. 6.2 СП 55 и п. 9.18 СП 55 нужно сверить по официальному тексту действующей редакции. Лучше всего — вместе с преподавателем строительных дисциплин или специалистом: часть фрагментов в открытых источниках неполная.
- **Модель не знает многого:** отделки, назначения помещений (если пользователь его не задал), реальных размеров помещений по стенам, нагрузок, свойств материалов по ГОСТ. Поэтому значительная часть выводов останется оценкой по модели.
- **Конструктивные проверки** (`heuristic`, `risk`) не заменяют расчёт. Опирание, пролёты, гибкость и простенки — признаки, при которых нужна оценка инженера.
- **Пороги профиля** (пролёты, гибкость, простенки) не нормативные. Их значения стоит согласовать с преподавателем под учебное задание.
- **IDS и IFC.** Совместимость с IDS не реализована и не проверена. Сохранение IFC4 проверено только на чтение файла ifcopenshell; передача в Renga, nanoCAD BIM и Pilot-BIM не проверялась.
- **Статус системы.** Предлагаемая система не сертифицирована и не подтверждает соответствие нормам. Её задача — находить дефекты модели, проверять сверенные пункты с прозрачной методикой и честно сообщать, когда вывод сделать нельзя.
